# Feature: crud-maker

Objective: Build `crud-maker`, an Angular 22 library in the melia gui/admin workspace that generates CRUD behavior from a simple, JSON-serializable config, with signal-based reactive state and best-practice architecture (reference: tymon/admin engine, weaknesses fixed). Since S7 the deliverable is a package family: `crud-maker` is logic only, and each UI library gets its own adapter package (`crud-maker-zorro`, later `crud-maker-primeng`) that the consumer installs or ignores.
Branch: feat/admin-crud-adapters (repo root: melZone; earlier work landed on feat/go-api)
Delivery strategy: ask-on-risk (slices ~400 authored lines, tests+code together; push/PR remain user decisions)
Test runner: `npx ng test crud-maker` (vitest, inside gui/admin workspace)

## Specs

- **S1** (verbatim): "vamos a crear una especie de libreria que se llame crud-maker para hacer los crud de manera rapida con un simple json de configuracion"
  - Acceptance: one serializable JSON config per entity defines fields, views (list/form/detail), filters, sort, pagination, actions; no TS classes with embedded functions.
- **S2** (verbatim): "puedes verificarlo en este repo /home/ivanare/proyects/tymon/admin/, mira como funcionan las paginas y los componentes (utilizaremos ng-zorro)"
  - Acceptance: reference architecture verified (see Log L2 handoff). Port the engine idea (attributes → table/form, fluent query, one generic controller). ng-zorro integration is deferred to T4 and must NOT leak into the base logic (UI-agnostic core).
- **S3** (verbatim): "primero haremos la base logica del crudmaker superoptimizado con las mejores practicas y el uso of signals para reactividad"
  - Acceptance: base logic = config schema + validation/normalization + signal state + CRUD engine over a pluggable transport. Uses Angular v22 best practices verified via `get_best_practices` MCP: signals + computed, no explicit OnPush/standalone flags, `@Service`, `inject()`, no `mutate`, pure derivations, strict types, no `any`.
- **S4** (derived from tymon weaknesses fix — the "mejores practicas" of S3 applied): 
  - A4.1 config is pure JSON → custom behaviors resolved by registered names, not embedded closures.
  - A4.2 one config per entity (single `fields` list with per-view flags), not duplicated table/form configs.
  - A4.3 per-instance controllers, not `providedIn:'root'` mutable singletons.
  - A4.4 no hard dependency on UI libs, auth, i18n or toast services in the core (interfaces/hooks).
  - A4.5 all list state (page, sort, filters, search, loading, error) is signal-backed and derived via computed; no NaN on unset pagination params.

- **S5** (verbatim, 2026-10-26): "los inputs aceptan getters para sobre escribir el valos en la tabla? ejemplo para renderizar un tag, o un badget en un campo de estaus" → approved "si dale" after the design answer (no getters — S4.1 holds; declarative hints instead).
  - Acceptance: optional serializable `cell: { render: 'text'|'badge'|'tag'|'dot', variantMap?: { value → variant } }` on FieldConfig; validated at define time; resolved default `{ render: 'text' }`; the library never emits markup — the UI layer interprets the hint. Demo renders `published` as a badge and `category` as a tag.
- **S6** (verbatim, 2026-10-26): "y los selects se llenan con ldata estatica o se puede colocar un endpoint para que se haga la cosnulta y se llene con es ainfo?" → approved "dale".
  - Acceptance: `OptionResolver` in the lib consumes the existing `{resource, labelField, valueField?}` metadata via the same `CrudTransport`; returns stable `Signal<FieldOption[]>` per resource; cached (one fetch per resource, shared); per-resource error signal (no silent empty); refresh(resource) re-fetches with stale-response protection; static options and non-select fields work without touching the transport. Demo: `category` switches to endpoint-driven options backed by a new `faq_categories` collection.

- **S7** (verbatim, 2026-10-31): "pero cambiamos el enfoque de ng-zorro, con crud maker vamos a crear un package a modo de logica para los componentes de front y con ng-zorro creamos otro paquete o dentro de crudmaker que yo pueda elegir al momento de instalar si elegir un paquete de front con los pauetes ya construidos como con ng-zorro o prime-ng o manual que no importa componentes"
  - Decision (user chose after the packaging tradeoffs were presented): **separate packages**, not secondary entrypoints of one package. `crud-maker` stays logic-only with zero UI dependencies; `crud-maker-zorro` and a future `crud-maker-primeng` are independent workspace projects whose `peerDependencies` are `crud-maker` plus their own UI library. "Manual" is not a package: it is core alone, and a consumer that wants its own components installs nothing else.
  - Acceptance: the install is the choice — `pnpm add crud-maker-zorro` (or `-primeng`, or neither) fully describes the UI decision in `package.json`; the core package declares no UI dependency and cannot import one (the dependency direction is adapter → core only); no adapter code ships in the core tarball; adding a third adapter touches no core source file.
- **S8** (derived from S7, the adapter contract): core owns everything that is presentation *logic*, adapters own everything that is presentation *library*.
  - Acceptance: pure, UI-free resolution of a field + raw value into a presentation view (`{ kind, text, variant }`) applying the registered formatter and the `variantMap`; a documented adapter surface (resolved config, controller signals and actions, list state, option signals) plus what an adapter must provide (table, form, detail, filters); every piece of it tested in the core suite with no DOM and no UI library.
- **S9** (derived from S7): `crud-maker-zorro` is the first adapter — table, form and detail screens built only against S8's contract. Requires explicit approval for `ng add ng-zorro-antd`.
- **S10** (derived from S7): `crud-maker-primeng` is deferred until the zorro adapter proves the contract. The package boundary makes it additive (new project + peer dependency), never a core change.

- **L15** (2026-10-31, T7.2): Added `crud-form` on Angular 22 Signal Forms. Three findings worth keeping:
  - `form()` injects, so it cannot be created inside a `computed`; the tree is built with `runInInjectionContext` against the component's own injector, cached per config, over a `linkedSignal` seeded from `value` so a new seed row reseeds the form without rebuilding the tree.
  - Native rules (`required`, `min`, `max`, `minLength`, `maxLength`, `pattern`, `email`) carry **no default message**: without `{message}` the error text is empty and a form looks broken while being correctly invalid. Every rule now sets an explicit English message, and a project-registered validator falls back to `validate()` with the compiled registry predicate.
  - `[formField]` is typed against the concrete value, so a dynamic field map needs `$any(bound(field))` in the template — the sanctioned escape for a genuinely dynamic binding, instead of `any` in the TS surface. Error display reads the field state (`bound(field)().touched()/errors()`) rather than a template ref, because refs declared inside `@switch` branches cannot be shared.
  - Evidence: adapter 21/21, core 91/91, app 11/11; adapter build 26949 B with `crud-maker` and `ng-zorro-antd/*` external; app bundle still 82.89 kB. `ng-zorro-antd` styles stay out of the SPA on purpose.
